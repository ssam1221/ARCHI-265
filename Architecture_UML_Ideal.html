Why refactor? — Pain points in the current code

The existing build works, but nearly all logic is concentrated in one file. The proposal below keeps everything that is already well-isolated (the pure-C detection core, the renderer, the rolling filters) and re-homes the rest into clear layers with one-way dependencies.

Design principles applied

Single Responsibility

Every class owns one reason to change. The 1541-line conductor becomes a handful of focused collaborators.

Dependency Inversion

Domain & application depend on interfaces (ports); Qt / audio / file / OS live in adapters that point inward.

Strategy Pattern

IAudioSource makes Mic / Playback / Synthetic interchangeable — deleting three duplicate workers.

Separation of Concerns

Capture ≠ detection ≠ analysis ≠ presentation ≠ rendering. Each is a distinct, replaceable seam.

RAII & Ownership

Smart pointers / value types replace new/delete & malloc/free; the C core is wrapped once at the boundary.

Testability

Domain analyzers run with no Qt, no audio hardware, no files — fed recorded event streams in unit tests.

Keep what's good: the pure-C libtimegrapher core (tg_context = HPF→Envelope→Detector→BPH/Sync) is already a clean facade with no Qt coupling, and SoundImageRenderer / RollingLeastSquares / RollingAverage are reusable. The refactor preserves these and builds clean seams around them.

Target Layered Architecture

Six concentric responsibilities. Solid arrows = compile-time dependency (who knows whom). Notice that everything points toward the Domain; infrastructure only attaches through ports.

Composition root: a small main() / AppBootstrap wires concrete adapters into the controller (which source, which detector, which mic configurator). Nothing else constructs infrastructure directly, so swapping a microphone backend or a detector never touches the domain.

The Dependency Rule

The single most important invariant of the target design: source-code dependencies may only point inward. The Domain knows nothing about Qt, audio APIs, files, or the OS.

RingDepends onNever depends on
Domain (analyzers, models, ports)Nothing (only the C++ stdlib)Qt, audio, files, the detection core
Application (controller, presenter)Domain + portsConcrete adapters, Qt widgets
Adapters (sources, detector, IO, platform)Ports they implement + Domain typesPresentation
Presentation (Qt views)Application (via presenter/controller)Domain internals, adapters

Target Threading Model

One capture thread, one source strategy, one encapsulated buffer. The three duplicated workers collapse into a single CaptureWorker parametrized by an injected IAudioSource.

Why this is safer: the consumer cursor lives in SessionController, not inside the shared buffer; the buffer exposes a narrow push()/pull() API guarding its own mutex; and lifecycle (start/requestStop/finished) is identical for every source, so there is exactly one place to get thread teardown right.

Target Runtime Sequence

A clean pass through the layers: capture → detect → analyze → present → render. Each hop crosses exactly one well-defined seam.
